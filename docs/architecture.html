execution architecture / appraisal

“Python versus compiled” is the wrong comparison.

scikit-learn is a layered system. Its public API is Python, but estimator hot paths variously execute in NumPy/SciPy, BLAS/LAPACK, sklearn-owned Cython/native code, or external native libraries such as liblinear and libsvm. Flow-scikit therefore classifies the substrate behind each benchmark before interpreting a speed result.

Evidence status. The table below is a static architecture appraisal of the algorithms in the canonical 19-row headline benchmark. It is deliberately labelled provisional until dynamic mixed-stack profiling from issue #184 measures runtime attribution. CI now requires every headline algorithm to retain an explicit classification; new benchmark algorithms cannot silently appear without one.

Python-bound

Material algorithm work really runs in CPython. Removing interpreter dispatch can be a direct advantage.

NumPy / SciPy-bound

Python mostly dispatches vectorized compiled kernels. Flow can target dispatch, allocation and fusion; it cannot call this “beating Python loops.”

BLAS / LAPACK-bound

Mature linear algebra dominates. The sensible default is to retain the kernel and compile/specialize around it, unless replacement is measured to be better.

sklearn-native-bound

Hot loops live in sklearn-owned Cython/C/C++. This is a compiled implementation contest, not interpreted versus compiled.

External-native-bound

liblinear/libsvm or another external native solver dominates. A Flow implementation must compete with that native baseline.

Mixed / boundary-heavy

Native kernels and Python orchestration both matter. Whole-estimator compilation may win through fusion, fewer crossings and fewer temporaries.

Appraisal

The current evidence is more interesting than a blanket “Flow is faster than Python” claim. Flow already wins 9 of 17 parity-eligible headline rows, including cases whose sklearn baseline is substantially compiled. That supports investigating whole-estimator compilation and lower integration overhead. At the same time, Flow loses badly on libsvm/liblinear-backed SVMs, Lasso, KernelRidge and several larger Digits workloads. Those losses show exactly why substrate matters: mature native kernels and scaling behaviour remain serious baselines.

The defensible claim today: Flow-scikit demonstrates competitive native implementations and striking wins on several end-to-end classical-ML workloads while using a much smaller deployment model. It does not yet demonstrate universal superiority over scikit-learn, NumPy/SciPy, BLAS/LAPACK, liblinear or libsvm. The next stage is to attribute runtime dynamically and separate kernel speed from orchestration, allocation and boundary costs.
